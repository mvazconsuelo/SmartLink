# Lab 02 — Cloudflare D1 and migrations

**Goal:** Persist data outside the cluster and change the schema without breaking the app.

## Idea

D1 is Cloudflare's managed SQL database (SQLite). It lives outside the cluster, so pods keep no state. The schema changes **only** through versioned migrations in `migrations/`, and each one is applied once.

## How it works

| Who | What it does |
| --- | --- |
| `scripts/03-d1.sh` | Creates the database (once) |
| Wrangler (in CI) | Applies pending migrations (`d1_migrations` records which ones) |
| Backend | Reads and writes data through the REST API |

```text
001_initial_schema   users, short_urls
002_add_expiration   expires_at column (nullable)
003_add_click_events click_events table
```

**Migration first, app second.** In `ci.yaml`, `migrate` runs before `gitops`. App v1 works with schema v2, but not the other way around. That is why migrations are **additive**: they add, they never rename or drop.

## Do it

Cloudflare dashboard → *D1 › smartlink › Console*:

```sql
SELECT name FROM d1_migrations;   -- 001, 002, 003
```

Add `migrations/004_add_title.sql` with `ALTER TABLE short_urls ADD COLUMN title TEXT;` and push. `migrate` applies it and the app keeps running.

## Break it

[💥 Failed migration](../break.md#5-failed-migration): invalid SQL → `migrate` fails → the deploy is blocked.

## Key points

- Infrastructure (script) ≠ schema (migrations) ≠ data (app).
- An applied migration is never edited: you fix it with a new one.
