# Lab 02 — Cloudflare D1 y migraciones

**Objetivo:** Persistir fuera del cluster y cambiar el schema sin romper la app.

## Idea

D1 es una base SQL administrada (SQLite) de Cloudflare. Vive fuera del cluster, así que los pods no guardan estado. El schema cambia **solo** con migraciones versionadas en `migrations/`, y cada una se aplica una vez.

## Cómo funciona

| Quién | Qué hace |
| --- | --- |
| `scripts/03-d1.sh` | Crea la base (una vez) |
| Wrangler (en CI) | Aplica migraciones pendientes (`d1_migrations` registra cuáles) |
| Backend | Lee y escribe datos por la REST API |

```text
001_initial_schema   users, short_urls
002_add_expiration   columna expires_at (nullable)
003_add_click_events tabla click_events
```

**Primero la migración, después la app.** En `ci.yaml`, `migrate` corre antes que `gitops`. App v1 funciona con Schema v2, pero no al revés. Por eso las migraciones son **aditivas**: agregan, no renombran ni borran.

## Hacelo

Dashboard de Cloudflare → *D1 › smartlink › Console*:

```sql
SELECT name FROM d1_migrations;   -- 001, 002, 003
```

Agregá `migrations/004_add_title.sql` con `ALTER TABLE short_urls ADD COLUMN title TEXT;` y pusheá. `migrate` la aplica y la app sigue andando.

## Rompelo

[💥 Migración fallida](../break.md#5-migración-fallida): SQL inválido → `migrate` falla → el deploy se bloquea.

## Clave

- Infraestructura (script) ≠ schema (migraciones) ≠ datos (app).
- Una migración aplicada no se edita: se corrige con otra nueva.
